# Give module linking its own deep module

Parent: [[issues-6-architecture-cleanup]]

## Blocked by

Prefer [[issues-8-deepen-frontend-compile-module]] first so call sites don’t re-grow link wiring.

## Description

Link (graph load, mangle, re-export, cycles) is a deep algorithm mis-homed under parser. Parser interface should be source → AST only.

## Affected

Parser crate public surface; anything calling `link_entry`; Frontend once it owns Script vs Module.

## Observed

~2k LOC link beside ~5k LOC parse. Different domain from recursive descent.

## Impact

ESM bugs look like parser failures; soft line limit impossible without split.

## Proposed Fix

Extract Linker module; Frontend chooses parse vs link.

## Agent Brief

### Goal

Give **module linking** its own deep module so **parser** interface is only syntax: source → Program AST.

### Contract

- Linker owns entry-path → linked/flattened Program (or equivalent current link output).
- Parser public API no longer presents link as a peer of parse on the same “this is the parser product” surface (re-exports removed or clearly deprecated only if needed for a short transition — prefer clean cut via Frontend).
- Link behavior and ESM conformance fixtures unchanged.
- Domain: keep “link” / module graph language consistent with existing docs; do not rename the language feature.

### Acceptance criteria

1. Link implementation lives outside the parser’s primary module surface (own module or crate).
2. Parser-focused docs/comments describe parse only; link is documented as Linker/Frontend concern.
3. All previous `link_entry` call sites compile via the new home (ideally only Frontend).
4. ESM-related conformance and parser/link tests green.
5. `cargo test --workspace` green.

### Out of scope

- Redesigning ESM semantics or mangling algorithm.
- Frontend compile module itself ([[issues-8-deepen-frontend-compile-module]]) — do that first if not done.
- Checker/IR changes.
