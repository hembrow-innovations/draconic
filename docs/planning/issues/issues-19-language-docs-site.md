# Language Learn + Reference site

## Description

People cannot learn Draconic or keep a working reference open while they write Programs. The README is clone-build-run. `docs/` is the agent vault. Roadmap **P03** is still `todo`.

This issue is the spec for the public site. Execute via child tracer tickets, not as one session.

Locked in [[0010-public-docs-draconic-ssg]] and `CONTEXT.md` (**Learn**, **Reference**).

## Problem Statement

Someone who already writes JavaScript or systems code has no public place to learn Dual worlds, modules, native types, host I/O, and packages, and no working Reference to keep open while they write a Program. The vault and the README are not that place.

## Solution

A static site generated by a Draconic Program. Sources are a markdown subset in a public tree. The site has two sections, Learn and Reference. Learn has two landings that join at Dual worlds, then the P03 chapters. Pages describe the language as designed and carry shipped or not-yet. Copy-paste code exists only on shipped pages and must build. CI generates HTML, compiles those fences, and publishes to GitHub Pages. The README stays the clone-build-run path and links here.

## User Stories

1. As a JavaScript or TypeScript programmer, I want a landing that assumes ECMAScript, so that I can reach Dual worlds without a beginner course.
2. As a systems programmer, I want a landing that assumes Rust, Go, or C, so that I can reach Dual worlds from the native side.
3. As either reader, I want those landings to join at Dual worlds, so that the rest of Learn is one path.
4. As a new toolchain user, I want an Install page, so that I can parse and build a Program before reading further.
5. As a learner, I want Learn chapters for modules, native types, host I/O, and packages, so that P03 is a real book skeleton, not an empty nav.
6. As someone writing a Program, I want a Reference section, so that I can look up CLI, types, Dual-world rules, host I/O, and packages without rereading Learn.
7. As a reader, I want Learn and Reference on one site with shared top nav, so that I can switch without hunting a second product.
8. As a reader, I want each page tagged shipped or not-yet, so that I know whether the chapter matches today's toolchain.
9. As a reader, I want not-yet pages to explain the designed language in prose, so that I can see where the language is going.
10. As a reader, I want copy-paste code only on shipped pages, so that I never paste a sample that will not build.
11. As a reader, I want not-yet pages to have no runnable fences, so that a status tag cannot lie next to a fake sample.
12. As an author, I want to write a markdown subset, so that long prose is writable without HTML or a page DSL.
13. As an author, I want frontmatter for title, section, and status, so that nav and tags are data, not hand-kept HTML.
14. As a maintainer, I want the generator to be a Draconic Program, so that the site dogfoods the language instead of Starlight or mdBook.
15. As a maintainer, I want the generator to emit static HTML, so that any host can serve it and GitHub Pages can publish it.
16. As a writer, I want a local generate step, so that I can see HTML before CI.
17. As a visitor, I want the public URL to be GitHub Pages from CI, so that the site exists without committing dist.
18. As a clone-from-README user, I want the README to keep write-parse-build and link to the site, so that onboarding and the book stay distinct.
19. As a CI job, I want shipped `drac` fences extracted and built, so that the must-build rule has teeth.
20. As a CI job, I want a not-yet page with a fence to fail, so that authors cannot sneak unrunnable samples past the tag.
21. As a JS-backend user, I want portable samples on shipped pages to build for js, so that the book matches the CLI I have.
22. As a native-target user, I want native-only shipped samples to build for native, so that Dual worlds and host I/O are not JS-only stories.
23. As someone who knows the vault exists, I want agent notes to stay out of the public tree, so that planning and ADRs do not leak into Learn.
24. As a later playground user, I want day one to stay static, so that we do not block the skeleton on an in-page runner.
25. As a complete beginner, I accept that this site is not for me yet, so that Learn does not become a programming course.
26. As a reader of a shipped chapter, I want headings, lists, links, and code fences to render, so that the subset is enough to teach.
27. As a navigator, I want every Learn chapter and every Reference stub linked from nav, so that the skeleton is walkable on day one.
28. As a Roadmap maintainer, I want **P03** marked done only when the pipeline is green and the README links the site, so that the checklist matches reality.

## Implementation Decisions

- Public sources live in a dedicated tree, not the agent vault. ADR-0010.
- The generator is a native Program: read pages, emit HTML. Same host I/O class as the todo static host, without requiring a live server for the published site.
- Page format: markdown subset only — headings, paragraphs, lists, fenced code, links — plus frontmatter for title, section (`learn` | `reference`), and status (`shipped` | `not-yet`).
- One site, two sections: Learn and Reference. Shared install page. No third product.
- Learn skeleton: Install; landing from JavaScript; landing from systems; Dual worlds (join); modules; native types; host I/O; packages.
- Reference skeleton: thin written pages for CLI, types, Dual-world rules, host I/O, packages — not a generated API dump.
- Designed-plus-status-tags: not-yet pages are prose. No code fence unless the page is shipped.
- Shipped fences are extracted and compiled in the same website pipeline that generates HTML.
- Publish: CI builds with Draconic, deploys HTML to GitHub Pages. Dist is not the source of truth.
- README remains clone-build-run and gains a link to the public site.
- This fulfills Roadmap **P03**. Child tickets are the execution atoms.
- No new compiler crate. The generator is a Program that uses existing host filesystem and the CLI build path.

## Testing Decisions

- One high seam: the website pipeline. Compile the generator, run it on the public tree, assert HTML; extract shipped fences and build them. Fail if a not-yet page contains a fence.
- Observe external behavior only: HTML structure (Learn and Reference nav, status, rendered subset) and `draconic build` success on shipped fences.
- Prior art: integration tests that compile example Programs (http-echo, todo server) and assert process or file results. Same height. Do not unit-test a markdown parser in Rust.
- A page with no shipped fence is still valid if it is not-yet and linked.

## Out of Scope

- Playground or in-page runner (later, as its own product).
- mdBook, Starlight, VitePress, or any Node docs generator as source of truth.
- Serving the agent vault as the public site.
- Full CommonMark, MDX, or a docs DSL in `.drac` files.
- Generated API reference from compiler symbols.
- Custom domain on day one.
- Teaching programming from scratch or a full ECMAScript tour.
- Committing generated HTML as the authoring format.
- REPL (already later, [[issues-4-language-product-polish]]).
- Flagship HTTP service example (**P04**).

## Further Notes

- Audiences are JS/TS programmers and systems programmers, not beginners. Two landings, one join at Dual worlds.
- Flagship apps stay under examples. Book fences are small Programs. Do not duplicate http-echo or todo as the book.
- Local static server in Draconic is optional sugar; GitHub Pages is the public host.
- Split this spec into tracer tickets before implementing. Do not implement the whole site in one session.
