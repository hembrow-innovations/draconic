# L10 Crypto later: HMAC + AEAD (after L03)

## Why

ROADMAP L10 locks HMAC + AEAD on both targets (stdlib location: honest portable libs a simple service needs). This row is later than the L v1 bar and sits after L03 SHA-256 digest; the cut is the parent row that HMAC-SHA256 and AEAD encrypt/decrypt form one later crypto library.

## Done

ROADMAP L10 is implemented test-first on both targets. A Program can HMAC-SHA256 a message with a key and AEAD encrypt/decrypt bytes (algorithm as designed) through the designed stdlib crypto surface. Invalid key, nonce, or ciphertext errors rather than silently succeeding. Tests under `tests/conformance` fixtures `stdlib/crypto` lock that combined surface. Mark L10 `done` only when those tests are green.

## Blocked by

[[s-l10-01]] and [[s-l10-02]]. L03 already landed (ROADMAP `done`; [[s-l03]] is archive-only). Parent remainder waits until HMAC-SHA256 and AEAD child atoms land so Build does not duplicate those Loops.

## Non-goals

- **L10.01**: HMAC-SHA256 (after L03)
- **L10.02**: AEAD encrypt/decrypt (after L03; algorithm as designed)
- **L03**: SHA-256 digest + secure random bytes
- **L03.01 / L03.02**: already `done` SHA-256 vectors and CSPRNG
- Web Crypto or Node `crypto` identity surface
- changing the L v1 done bar to require L10
