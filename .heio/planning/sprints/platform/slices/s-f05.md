# F05 Link/load dynamic lib (`.so`/`.dylib`/`.dll`); call one symbol

## Why

ROADMAP F05 locks native dynamic linking on the Dual-world FFI boundary (ADR-0002 shared IR, ADR-0003 dual worlds). A Program can load one external `.so`/`.dylib`/`.dll` and call one C symbol without leaving Draconic. F05.01–F05.02 already land load/resolve-one-symbol and call-with-typed-missing-lib error; this cut is the parent row that those ops form one honest link-dynamic / call-one-symbol surface. F05 deepens the F v1 bar.

## Done

ROADMAP F05 is implemented test-first on native. Native build loads an external dynamic library (`.so`/`.dylib`/`.dll`), resolves one C symbol, and calling that symbol observes the C return value end-to-end; a missing lib is a typed error. Tests under `tests/conformance` fixtures `ffi/link_dynamic` and `tests/integration` lock that combined surface. Mark F05 `done` only when those tests are green.

## Blocked by

None.

## Non-goals

- **F05.01**: Load dynamic lib at link or runtime; resolve one symbol (already `done`)
- **F05.02**: Call dynamic symbol; missing lib → typed error (already `done`)
- **F04**: Link external static lib (`.a`)
- **F02**: C callbacks (Draconic fn as `extern "C"` pointer)
- **F03**: C-compatible struct layout
- **F07**: Bindgen from C headers
- **F08**: Unsafe/native-only FFI diagnostics (js hard-error)
- **F09**: wasm32/wasi emit
- js-target FFI (native-only until an explicit bridge row)
