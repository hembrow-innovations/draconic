# C04 Parallel `draconic test`: multi-fixture workers; deterministic aggregate exit

## Why

ROADMAP C04 locks parallel `draconic test` on the compiler (concurrency location: workers/isolates a team can ship simple services with; C04 is tooling). C04.01–C04.02 already land a worker pool (N>1) for multi-fixture runs and deterministic aggregate exit plus stable failure summary order; this cut is the parent row that those ops form one honest parallel-test surface. C04 is tooling, not the C v1 done bar.

## Done

ROADMAP C04 is implemented test-first on the compiler. `draconic test` runs fixtures on a worker pool (N>1, including default and `--jobs`), any fixture failure yields aggregate exit 1 even with passing siblings, and FAIL summary order is stable by fixture id across runs. Tests under `crates/draconic-cli` and `tests/integration` lock that combined surface. Mark C04 `done` only when those tests are green.

## Blocked by

None. C04.01 and C04.02 already land the per-class worker-pool and aggregate-exit tests this parent row unifies.

## Non-goals

- **C04.01**: `draconic test` runs fixtures on worker pool (N>1) (already `done`)
- **C04.02**: Deterministic aggregate exit code + stable failure summary order (already `done`)
- **C01**: Worker / OS thread spawn isolate
- **C02**: Message-passing channels
- **C03**: `once` / thread-safe init
- **C05**: Structured cancellation / timeout helpers
- **C06**: Shared-memory atomics (later; not v1 bar)
- **L05**: In-language test framework
- Test262 runner parallelism (S02 / E19.02)
