# L10.01 HMAC-SHA256 (after L03)

## Why

ROADMAP L10.01 locks HMAC-SHA256 on both targets (stdlib location: honest portable libs a simple service needs). This row is later than the L v1 bar and sits after L03 SHA-256 digest; the cut is one atomic Loop so a Program can HMAC-SHA256 a message with a key through the designed crypto surface.

## Done

ROADMAP L10.01 is implemented test-first on both targets. A Program can compute HMAC-SHA256 over bytes with a key, matching known test vectors, through the designed stdlib crypto surface. Invalid key or message input errors rather than silently succeeding. Tests under `tests/conformance` fixtures `stdlib/crypto` lock that HMAC-SHA256 surface. Mark L10.01 `done` only when those tests are green.

## Blocked by

None. L03 already landed (ROADMAP `done`; [[s-l03]] is archive-only).

## Non-goals

- **L10**: parent Crypto later HMAC + AEAD remainder
- **L10.02**: AEAD encrypt/decrypt (algorithm as designed)
- **L03**: SHA-256 digest + secure random bytes (parent unify)
- **L03.01 / L03.02**: already `done` SHA-256 vectors and CSPRNG
- Web Crypto or Node `crypto` identity surface
- changing the L v1 done bar to require L10
