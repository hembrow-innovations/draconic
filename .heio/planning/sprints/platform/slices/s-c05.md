# C05 Structured cancellation / timeout helpers on async work (channels + timers)

## Why

ROADMAP C05 locks structured cancellation and timeout helpers on both targets (concurrency location: workers/isolates a team can ship simple services with; C05 after H05). C05.01–C05.02 already land Abort-like cancel tokens that propagate to async work and a timeout helper that races work vs timer; this cut is the parent row that those ops form one honest cancel/timeout surface.

## Done

ROADMAP C05 is implemented test-first on both targets. A Program can make a cancel token, abort it (sticky/idempotent), link child tokens so abort propagates, and race async work against a timer via `withTimeout` / `clearWithTimeout` so the loser settles cleanly. Tests under `tests/conformance` fixtures `concurrency/cancel` lock that combined surface. Mark C05 `done` only when those tests are green.

## Blocked by

None. C05.01 and C05.02 already land the per-class cancel-token and timeout fixtures this parent row unifies. H05 timers are already green on the child row C05.02 needs.

## Non-goals

- **C05.01**: Cancel token / Abort-like signal: propagate to async work (already `done`)
- **C05.02**: Timeout helper: race work vs timer (needs **H05**); settle cleanly (already `done`)
- **C01**: Worker / OS thread spawn isolate
- **C02**: Message-passing channels
- **C03**: `once` / thread-safe init
- **C04**: Parallel `draconic test`
- **C06**: Shared-memory atomics (later; not v1 bar)
- Node `AbortController` / `AbortSignal` identity or a new host timer API beyond H05
