# C03 `once` / thread-safe init; mutex only if Runtime internals need it

## Why

ROADMAP C03 locks native `once` / thread-safe init and Runtime-internal mutex only where required (concurrency location: no user-facing shared JS heap). C03.01–C03.02 already land the once primitive and internal mutex; this cut is the parent row that those ops form one honest native sync surface. C03 is tooling, not the C v1 done bar.

## Done

ROADMAP C03 is implemented test-first on native. A Program can use thread-safe `once` init (`makeOnce` / `onceRun`). Runtime uses an internal mutex only where required, not as a user-facing shared-heap lock. Tests under `crates/draconic-runtime` and `tests/conformance` fixtures `concurrency/sync` lock that combined surface. Mark C03 `done` only when those tests are green.

## Blocked by

None. C03.01 and C03.02 already land the per-class once and mutex tests this parent row unifies.

## Non-goals

- **C03.01**: `once` / thread-safe init primitive (already `done`)
- **C03.02**: Runtime-internal mutex only where required (already `done`)
- **C01**: Worker / OS thread spawn isolate
- **C02**: Message-passing channels
- **C04**: Parallel `draconic test`
- **C05**: Structured cancellation / timeout helpers
- **C06**: Shared-memory atomics (later; not v1 bar)
- user-facing shared JS heap or a public mutex Host API
